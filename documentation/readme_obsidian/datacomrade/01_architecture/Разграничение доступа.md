# Разграничение доступа

Права выдаются **двумя независимыми параллельными путями**, а не прямым отображением «роль Keycloak → таблица».

Обе связки грантов ([[dc.user_domain_roles]] и [[dc.user_table_roles]]) — трёхсторонние: одна строка сразу фиксирует пользователя, роль и объект (домен или таблицу). Раньше между ролью и объектом стояла отдельная промежуточная таблица (`dc.domains_domain_roles`, `dc.tables_table_roles`); в текущей схеме она удалена, а `domain_id`/`table_id` перенесены прямо в связку с пользователем.

## Путь 1: через домен (крупная гранулярность)

[[dc.user_domain_roles]] (`user_id` + `domain_roles_id` + `domain_id`) → [[dc.domain_cat]] → все таблицы этого домена.

Работает потому, что `table_cat.domain_id` жёстко привязывает каждую таблицу ровно к одному домену.

## Путь 2: через таблицу (точечно)

[[dc.user_table_roles]] (`user_id` + `table_roles_id` + `table_id`) → [[dc.table_cat]].

Даёт доступ к конкретной таблице напрямую, в том числе к таблице из домена, к которому доменного доступа нет.

## Эффективный доступ

```
доступные таблицы = таблицы(доменные роли) ∪ таблицы(табличные роли)
```

Модель deny-by-default: таблица, не покрытая ни одним путём, не видна ни в конструкторе, ни при прямом обращении к API.

## Где проверяется

| Точка | Что проверяет |
| --- | --- |
| [[API Gateway]] | Доступны ли вообще административные методы — по realm-роли из JWT: `admin` → `userdomainrolesapiv1` (просмотр пользователей, назначение прав), `maintainer` → `tablesapiv1` (правка каталога), `viewer` — без спецправ |
| [[Query Builder Service]] | Входит ли каждая запрошенная таблица в эффективный доступ — до генерации SQL |

Административный доступ и доступ к данным разделены концептуально: `admin`/`maintainer` в Keycloak — это право администрировать каталог и права пользователей, а не автоматическое право читать все данные.

## Ограничение: нет прав на уровне поля

Гранулярность модели — домен и таблица. На уровне колонки есть только `column_cat.show_in_ui` — глобальный флаг видимости, одинаковый для всех пользователей. Требование «разным пользователям разный набор колонок внутри одной разрешённой таблицы» текущей схемой **не закрывается**; для него понадобится таблица вида `user_column_roles` / `columns_column_roles` по образцу табличных ролей. См. [[Замечания к реализации]].
