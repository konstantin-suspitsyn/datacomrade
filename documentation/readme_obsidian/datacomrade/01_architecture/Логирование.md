# Логирование

## Что уже есть

Общий логгер `platform/pkg/logger` на `zap`:

- JSON- или консольный вывод в stdout, уровень и формат берутся из env (`DATACATALOGUE_LOGGER_LEVEL`, `DATACATALOGUE_LOGGER_AS_JSON`) — см. [[Работа с env файлами]].
- Динамическая смена уровня в рантайме (`SetLevel`).
- Обогащение записи полями `trace_id` и `user_id` из `context.Context`.

Вывод JSON в stdout — правильная база: контейнер пишет в stdout, сборщик логов забирает оттуда, файлы и ротация не нужны.

## Пробел закрыт для Shepherd, но не везде

`platform/pkg/logger` теперь экспортирует `ContextWithTraceID`/`ContextWithUserID` — раньше ключи и тип `Key` были неэкспортированы, и обогащение никогда не срабатывало (см. [[Замечания к реализации]] п.4). [[API Gateway]] (`shepherd`) использует `ContextWithTraceID`: `requestlog`-middleware кладёт `trace_id` (входящий заголовок `X-Trace-Id` или новый uuid) на входе в цепочку. `ContextWithUserID` пока не используется — резолв `user_id` больше не middleware, а явный вызов внутри `meapiv1.GetMe`/`loginapiv1.Login` (см. [[API Gateway]], «Автосоздание пользователя»), которые пока не логируют через `platform/pkg/logger`.

`datacatalogue` этот логгер вообще не подключён — сервис пишет через stdlib `log`, а не `platform/pkg/logger`. Перевести его — отдельная, не блокирующая задача.

## Правила

- Один `trace_id` на весь путь Gateway → Builder → Executor, тот же ID уходит в трейсы ([[Мониторинг]]).
- **Не логировать значения параметров запроса и строки результата.** Это пользовательские данные из целевых баз. Логируем шаблон SQL, хеш запроса, идентификатор базы, число строк и длительность.
- Ошибки от целевых СУБД логировать целиком в `error`, но следить, чтобы текст ошибки не содержал значений (некоторые драйверы подставляют их в сообщение).
- Уровни: `debug` — сгенерированный SQL (только в dev-контурах), `info` — факт запроса и его метрики, `warn` — сработавшие лимиты и отказы по правам, `error` — сбои подключения и выполнения.

## Сбор

Логи JSON из stdout → Promtail (или Vector) → Loki → просмотр в Grafana рядом с метриками. Поиск по `trace_id` связывает лог, трейс и метрику одного запроса.

## Аудит — это не логи

События «кто какие данные запросил» идут отдельным потоком через брокер в Audit Service, а не в Loki. У аудита другие требования: срок хранения, неизменяемость, выборки по пользователю. Смешивать его с техническими логами, которые ротируются через 30 дней, нельзя.
