# Замечания к реализации

Разбор расхождений между задуманной архитектурой и тем, что сейчас в коде и миграциях. Отсортировано по серьёзности.

## 1. Глобальная уникальность имени колонки — блокирующая

`000000020_create_table_column_cat.sql`:

```sql
CONSTRAINT column_cat_name_unique UNIQUE ("name")
```

Ограничение стоит на `name` без `table_id`. То есть во всём каталоге может существовать только одна колонка с именем `id`, одна `created_at`, одна `name`. Вторая же зарегистрированная таблица упрётся в конфликт.

Нужно: `UNIQUE (table_id, name)`.

## 2. Глобальная уникальность имени таблицы — блокирующая

`000000009_create_table_cat.sql`:

```sql
CONSTRAINT table_cat_name_unique UNIQUE (name)
```

Та же проблема уровнем выше: две схемы или две базы не могут содержать таблицу `orders`. Для мультибазовой системы это неверно по определению.

Нужно: `UNIQUE (schema_id, name)`.

## 3. Нет графа связей для JOIN

Конструктор позволяет выбрать поля из нескольких таблиц, но в каталоге нет явного описания, **как** эти таблицы соединять. Есть косвенные кандидаты:

- [[dc.alias]] — «одинаковые по смыслу» колонки в разных таблицах;
- [[dc.has_to_gpoup]] — пары `column_id_a` / `column_id_b` без FK и без описанной семантики;
- [[dc.table_type]] — `fact` / `dimension`, то есть подразумевается звезда.

Пока правила соединения не заданы явно (какая колонка факта к какой колонке измерения, тип join, кардинальность), [[Query Builder Service]] не сможет детерминированно построить многотабличный запрос — он будет угадывать. Это стоит закрыть до реализации Builder, иначе логика расползётся по коду.

## 4. ~~Логгер не может получить trace_id и user_id~~ — исправлено для Shepherd

`platform/pkg/logger` теперь экспортирует `ContextWithTraceID`/`ContextWithUserID`; [[API Gateway]] их использует в `requestlog`/`ensureuser` middleware. `datacatalogue` на этот логгер по-прежнему не переведён (пишет через stdlib `log`) — см. [[Логирование]].

## 5. Имена переменных окружения в `host` мешают добавлять источники в рантайме

[[dc.host]] хранит имена env-переменных (`host_env`, `port_env`, `username_env`, `password_env`), а значения приходят из окружения. Для фиксированного набора источников это работает и держит секреты вне БД — правильно.

Но администратор не сможет добавить новый источник через API «на лету»: сначала нужно прописать переменные в окружение и передеплоить [[Query Execution Service]]. Если сценарий «добавить базу без релиза» нужен — потребуется secret manager (Vault) с ссылкой на секрет вместо имени переменной. Решение осознанное, просто оно должно быть зафиксировано.

## 6. Нет прав на уровне колонки

`column_cat.show_in_ui` — глобальный флаг, одинаковый для всех пользователей. Разграничение работает до уровня таблицы. Подробнее: [[Разграничение доступа]].

## 7. Каталог не описывает специфику ClickHouse

Для корректной генерации SQL под ClickHouse в каталоге не хватает:

- признака «нужен `FINAL`» (движки семейства `ReplacingMergeTree`);
- пометки «агрегация приблизительная» у `uniq` / `quantile` — чтобы UI показывал это пользователю;
- признака, что измерение доступно как словарь (`dictGet`) вместо join.

См. [[Поддерживаемые СУБД]].

## 8. Мелочи

- `dc.has_to_gpoup` — опечатка в имени таблицы и файла миграции (`gpoup` вместо `group`). Чем дольше живёт, тем дороже переименование.
- В [[dc.database_calculation]] не заданы FK на `database_cat`, `calculation_type`, `user` — связи только логические.
- `column_cat.calculation_type_id` объявлен `NOT NULL`: значит для колонок-измерений нужна строка-заглушка вроде `none` в [[dc.calculation_type]]. В самой миграции есть комментарий, что проверку соответствия типу базы надо делать на backend — это ровно то, за что отвечает матрица [[dc.database_calculation]].
- Redis в `deploy/compose` пока нет — см. [[Кеширование Redis]].

## 9. `CreateUser` в Metadata Service не идемпотентен

`external_id` в [[dc.user]] уникален (`user_external_id_unique`), но `CreateUser` — обычный `INSERT` без `ON CONFLICT`. При двух параллельных первых запросах одного нового Keycloak-пользователя (сценарий автосоздания в [[API Gateway]]) второй `INSERT` падает на уникальном ограничении.

Сейчас компенсируется на стороне Gateway: ошибка создания → один повторный `GetUserByExternalId`. Правильнее — сделать `CreateUser` upsert'ом (`INSERT ... ON CONFLICT (external_id) DO UPDATE ... RETURNING`), тогда Gateway обходится одним RPC вместо Get+Create+retry.
