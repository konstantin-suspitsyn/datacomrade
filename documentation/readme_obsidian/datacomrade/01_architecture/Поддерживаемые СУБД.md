# Поддерживаемые СУБД

Система работает с несколькими типами целевых баз. Тип конкретной базы хранится в [[dc.database_type]], сама база — в [[dc.database_cat]].

| СУБД | Драйвер Go | Назначение |
| --- | --- | --- |
| PostgreSQL | `pgx` | OLTP-источники, MVP |
| MySQL | `go-sql-driver/mysql` | OLTP-источники, MVP |
| MSSQL | `denisenkom/go-mssqldb` | Фаза 2 |
| Oracle | `godror` (CGO + Instant Client) | Фаза 2 |
| ClickHouse | `ClickHouse/clickhouse-go/v2` | OLAP, аналитические витрины |

## ClickHouse — почему он здесь особенный

ClickHouse — не «ещё один диалект в списке», а единственная в списке OLAP-СУБД, и именно под неё продукт (self BI поверх схемы fact/dimension) подходит лучше всего. Но правила генерации SQL для него отличаются сильнее, чем между Postgres и MySQL.

**Приблизительные агрегации.** `uniq()`, `uniqCombined()`, `quantile()` считают приближённо. Это не баг: так ClickHouse получает скорость. Но для BI это означает, что число в отчёте может слегка отличаться от «точного» `count(distinct)`. В UI такие агрегации нужно помечать как приблизительные, иначе пользователь получит тихо неверные цифры и потеряет доверие к системе. Точный аналог — `uniqExact()`, он медленнее.

Именно из-за этого таблица [[dc.database_calculation]] (какие типы вычислений поддерживает конкретная база) перестаёт быть формальностью: набор доступных агрегаций у ClickHouse и Postgres реально разный, и [[Query Builder Service]] обязан сверяться с этой матрицей.

**JOIN.** ClickHouse умеет join, но он дороже и семантически беднее, чем в Postgres: правая таблица целиком грузится в память. Для звезды `fact` + `dimension` (см. [[dc.table_type]]) это значит, что джойн к большому измерению может «положить» запрос. Практика — денормализация или словари (`dictGet`). Builder должен либо ограничивать число join на ClickHouse, либо уметь подставлять `dictGet` там, где измерение оформлено словарём.

**FINAL.** Для движков семейства `ReplacingMergeTree` без `FINAL` могут вернуться дубли (схлопывание идёт в фоне). Признак «нужен ли FINAL» — это свойство таблицы, которого сейчас нет в [[dc.table_cat]]; см. [[Замечания к реализации]].

**Прочее.** Идентификаторы — обратные кавычки или двойные; имена функций регистрозависимы; `LIMIT/OFFSET` работает как в Postgres (проще, чем `FETCH`/`TOP` у Oracle и MSSQL); есть `PREWHERE` как оптимизация фильтрации.

**Лимиты выполнения ложатся отлично.** Настройки сессии `readonly=1`, `max_execution_time`, `max_result_rows`, `max_memory_usage` ровно закрывают гарантии, которые [[Query Execution Service]] должен давать на любой базе.

## Что это значит для генерации SQL

Диалект-независимое дерево запроса (AST) остаётся общим, но рендер под ClickHouse — это отдельный адаптер, а не «Postgres с другими кавычками». Нужен тестовый набор «один и тот же логический запрос → пять диалектов» с эталонными результатами.
