# Кеширование Redis

Redis — общий кеш-слой. Ниже — что именно кешируем, с каким ключом и как инвалидируем. Всё, чего нет в таблице, не кешируется.

| Данные | Кто пишет | Ключ | TTL | Инвалидация |
| --- | --- | --- | --- | --- |
| Дерево доступных таблиц/колонок пользователя | [[Metadata Service]] | `acl:tree:{user_id}` | 10–15 мин | По событию изменения прав или каталога |
| Справочники (`calculation_type`, `column_type`, `table_type`, `database_type`) | [[Metadata Service]] | `dict:{name}` | 1 час | По событию записи в справочник |
| Матрица `database_calculation` | [[Metadata Service]] | `dbcalc:{database_cat_id}` | 1 час | По событию записи |
| JWKS-ключи Keycloak | [[API Gateway]] | `jwks:{realm}` | по `Cache-Control` Keycloak | По ротации ключей |
| Счётчики rate limit | [[API Gateway]] | `rl:{user_id}:{window}` | размер окна | Не требуется |
| Резолв пользователя (`external_id → user_id`) | [[API Gateway]] | `user:known:{external_id}` | ~30 мин | По TTL |
| Результаты запросов (опционально) | [[Query Execution Service]] | `res:{sha256(sql+params+db_id)}` | 1–5 мин | По TTL |

## Почему инвалидация по событию, а не только TTL

Для прав доступа TTL недостаточно. Окно «администратор забрал доступ, но кеш ещё 15 минут отдаёт старое дерево» — это не задержка согласованности, а дыра в безопасности. Поэтому запись в таблицы прав и каталога должна публиковать событие инвалидации (через тот же брокер, что и аудит), а подписчики — сбрасывать соответствующие ключи.

Практичный компромисс: инвалидация по событию как основной механизм + короткий TTL как страховка на случай потери события.

## Кеш резолва пользователя — тут TTL-only это нормально

В отличие от дерева прав, промах кеша `user:known:{external_id}` не открывает дыру в безопасности: он не хранит права, только факт «эта строка в [[dc.user]] уже существует, вот её `user_id`». Худший случай при устаревшем/отсутствующем ключе — одна лишняя проверка в [[Metadata Service]] на следующий запрос, не более. Событийная инвалидация здесь не нужна.

## Кеш результатов запросов — с оговорками

Ключ обязан включать идентификатор целевой базы и хеш параметров, а не только текст SQL. Кешировать по `user_id` не нужно: если два пользователя получили одинаковый SQL, значит проверка прав в [[Query Builder Service]] уже пропустила их обоих к одним и тем же данным — данные идентичны по построению.

Два ограничения:

- Ставить потолок на размер кешируемого ответа (например, 1 МБ). Выгрузка на сотни тысяч строк в Redis не должна попадать вообще — иначе кеш вытеснит полезные ключи и упрётся в память.
- Не включать этот кеш для источников с быстро меняющимися данными без явного согласия владельца домена: пользователь, дважды нажавший «обновить», не должен видеть залипший результат.

## Чего не кешируем

Рендер AST → SQL. Он дешёвый и чистая функция от входа; кеш здесь добавит инвалидационную сложность без выигрыша.

## Эксплуатация

Redis — кеш, а не хранилище: политика `allkeys-lru`, потеря инстанса должна приводить к деградации производительности, но не к ошибкам. Любой путь чтения обязан корректно отрабатывать при недоступном Redis (fallback в Postgres). Метрики попаданий — в [[Мониторинг]].
