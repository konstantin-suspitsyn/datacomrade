# Миграции БД

Миграции всех микросервисов накатываются через [goose](https://github.com/pressly/goose) из корневого `Taskfile.yml` — руками в папку микросервиса заходить больше не нужно. Общее устройство задач — [[Taskfile]].

## Команды

| Команда | Что делает |
| --- | --- |
| `task migrate:up` | накатывает миграции **всех** микросервисов |
| `task migrate:up:datacatalogue` | накатывает миграции только `datacatalogue` — [[Goose]] |

```bash
task migrate:up
```

Отдельный микросервис:

```bash
task migrate:up:datacatalogue
```

Перед первым запуском бинарник `goose` ставится автоматически в `bin/` под-таском `install-goose` (версия — переменная `GOOSE_VERSION` в `Taskfile.yml`). Повторно он не переустанавливается: у задачи есть `status: test -x {{.GOOSE}}`.

Миграции накатываются на уже поднятую БД, поэтому сначала `task up-all` (или `task up-core`) — см. [[Перезапуск микросервисов - рабочий процесс]].

## Как это устроено

`migrate:up` — задача-диспетчер, она ничего не мигрирует сама, а по очереди вызывает под-таски `migrate:up:<микросервис>`. Тот же приём используется в `sqlc:gen` — см. [[sqlc_generation]].

Под-таск микросервиса делает ровно две вещи:

- `dir: <микросервис>` — переходит в папку микросервиса;
- `goose up` — goose по умолчанию читает `.env` из текущей директории (флаг `-env`, значение по умолчанию `.env`), поэтому все настройки подключения берутся из `<микросервис>/.env`.

Никаких путей и строк подключения в `Taskfile.yml` не хранится — только в `.env`, который генерируется из `deploy/env/params.toml` (см. [[Работа с env файлами]]).

### Переменные goose в `.env`

| Переменная | Назначение |
| --- | --- |
| `GOOSE_DRIVER` | драйвер БД (`postgres`) |
| `GOOSE_DBSTRING` | строка подключения |
| `GOOSE_MIGRATION_DIR` | папка с миграциями относительно микросервиса (`./db/migrations`) |
| `GOOSE_TABLE` | таблица с историей применённых миграций (`tech.goose_migrations`) |

## Добавление нового микросервиса

1. Завести в `deploy/env/params.toml` секцию `<микросервис>.goose` с четырьмя переменными выше и перегенерить env — `task env:gen`.
2. Положить миграции в `<микросервис>/db/migrations`.
3. Добавить в `Taskfile.yml` задачу по образцу `datacatalogue`:

```yaml
  migrate:up:<микросервис>:
    deps: [install-goose]
    desc: "Применяет миграции БД для <микросервис>"
    dir: <микросервис>
    cmds:
      - "{{.GOOSE}} up"
```

4. Добавить её вызов в диспетчер `migrate:up`:

```yaml
  migrate:up:
    cmds:
      - task: migrate:up:datacatalogue
      - task: migrate:up:<микросервис>
```

## Прочие команды goose

Задачами обёрнут только `up` — остальное пока запускается бинарником из `bin/` в папке микросервиса (`.env` подхватится сам):

```bash
cd datacatalogue
../bin/goose status
```

Полезное: `status` (что накачено), `version` (текущая версия БД), `down` (откатить одну миграцию), `validate` (проверить файлы, не выполняя их).
