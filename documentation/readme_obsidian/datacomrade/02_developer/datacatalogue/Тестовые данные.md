# Тестовые данные

Пара скриптов, наполняющих схему `dc` связным тестовым набором и убирающих его за собой:

| Файл | Назначение |
| --- | --- |
| `datacatalogue/db/other_queries/test_sqls/insert_test_data.sql` | Вставка тестовых данных |
| `datacatalogue/db/other_queries/test_sqls/delete_test_data.sql` | Удаление ровно того, что вставил первый |

Это не миграции: [[Goose]] их не видит и не применяет. Запускаются руками на локальной или тестовой базе поверх уже накатанных миграций.

## Соглашение о префиксе

Всё держится на одном правиле: **каждая именованная тестовая сущность создаётся с префиксом `test_`**. Удаление ищет строго по этой маске.

```sql
WHERE "name" LIKE 'test\_%'
```

Обратный слеш обязателен. В `LIKE` символ `_` — это wildcard на любой один символ, и маска `'test_%'` поймала бы, например, домен `testing_sales`. С экранированием совпадает только буквальный `test_`.

Сущности без собственного имени — [[dc.column_cat]], [[dc.group_levels]], [[dc.has_to_gpoup]], связки ролей, `dc.database_calculation`, `dc.following_calculation` — удаляются только через связь с родителем, помеченным префиксом. Колонки специально названы реалистично (`order_id`, `amount`), без префикса: единственный корректный критерий для них — принадлежность тестовой таблице.

## Что не трогается

Скрипты не вставляют и не удаляют справочные данные, засеянные миграциями:

- [[dc.calculation_type]] — `sum`, `count`, `count_distinct`, `avg`, `max`, `min` (миграция 40);
- [[dc.table_type]] — `fact`, `dimension` (миграция 44);
- [[dc.domain_roles]] и [[dc.table_roles]] — `can_read`, `can_write`, `can_grant` (миграции 45 и 46);
- [[dc.user]] — `Lomonosov M.` (миграция 43).

Справочники только читаются по имени при вставке. Ни у одной из этих строк нет префикса `test_`, поэтому под маску удаления они не попадают.

## Права доступа в наборе

Набор построен так, чтобы разобрать оба пути из [[Разграничение доступа]]:

| Пользователь | Путь 1 (домен) | Путь 2 (таблица) | Ожидаемый эффективный доступ |
| --- | --- | --- | --- |
| `test_user_admin` | sales + finance | payments, orders | все 4 таблицы |
| `test_user_reader` | sales | payments | 4 таблицы, причём `test_tbl_payments` — только точечной выдачей |
| `test_user_writer` | sales | orders | 3 таблицы, `test_tbl_payments` недоступен |
| `test_user_no_roles` | — | — | пусто (deny-by-default) |

`test_user_reader` — главный кейс: он читает таблицу из домена, к которому доменного доступа у него нет. Ровно тот сценарий, ради которого путь 2 и существует. `test_user_no_roles` намеренно оставлен без единой роли.

## Запуск

Вставка:

```bash
docker exec -i datacomradepostgres psql -U postgres_user -d dcat -v ON_ERROR_STOP=1 < datacatalogue/db/other_queries/test_sqls/insert_test_data.sql
```

Удаление:

```bash
docker exec -i datacomradepostgres psql -U postgres_user -d dcat -v ON_ERROR_STOP=1 < datacatalogue/db/other_queries/test_sqls/delete_test_data.sql
```

Имя контейнера и креды берутся из `deploy/compose/datacatalogue/.env` — см. [[Работа с env файлами]]. `ON_ERROR_STOP=1` нужен обязательно: без него psql проглотит ошибку в середине и продолжит, а оба скрипта обёрнуты в `BEGIN` / `COMMIT` и рассчитывают на остановку.

## Свойства скриптов

**Идемпотентность.** Повторный запуск вставки даёт 20 стейтментов по 0 строк, повторный запуск удаления — то же самое. Достигнуто через `ON CONFLICT DO NOTHING` там, где есть unique-констрейнт, и `NOT EXISTS` там, где его нет ([[dc.schema_cat]], связки, `*_calculation`).

**Никаких захардкоженных id.** Все FK разрешаются подзапросами по уникальным именам, поэтому скрипты не зависят от текущих значений sequence и не могут промахнуться по чужой записи с подходящим id.

**Порядок удаления — от детей к родителям.** Все FK объявлены `ON DELETE RESTRICT`, каскадов нет, так что порядок в `delete_test_data.sql` менять нельзя.

**Падение вместо тихой зачистки.** Родители удаляются строго по маске, без расширения «всё, что лежит внутри тестовой схемы». Если кто-то положит в `test_schema_marts` нетестовую таблицу, удаление упрётся в FK и упадёт. Это осознанный выбор: явная ошибка лучше молчаливого удаления чужих данных.

## Проверка перед удалением

В конце `delete_test_data.sql` лежит закомментированный `SELECT`, показывающий поимённо всё, что попадёт под маску. Стоит прогнать его перед удалением на базе, где кроме тестовых данных есть что-то ещё. Симметричный блок в конце `insert_test_data.sql` сверяет количества после вставки.

## Ограничение: имена ролей

Роли в наборе заведены на каждый объект (`test_role_domain_sales_read`), а не переиспользованы глобальные `can_read` / `can_write` / `can_grant` из миграций 45 и 46.

Причина в том, что имя роли уникально глобально, а в связках [[dc.user_domain_roles]] и [[dc.domains_domain_roles]] нет ни одного общего поля, кроме самой роли. При глобальных ролях привязка «конкретный пользователь к конкретному домену» не выражается вовсе: любой пользователь с `can_read` читает любой домен, к которому прицеплена `can_read`. Гранулярность из [[Разграничение доступа]] получается только при роли на объект.

Развилка архитектурная и в наборе не решается — она просто зафиксирована выбором имён. Любой запрос эффективного доступа, написанный под глобальные роли (с фильтром `name = 'can_read'`), на этих данных вернёт пусто. Смежные пункты: [[Замечания к реализации]].
