# Необязательные стандартные операции и пагинация — как это реально устроено

Дополнение к [generate_gprpc_go.md](generate_gprpc_go.md), [pagination_go.md](pagination_go.md)
и [pagination_proto.md](pagination_proto.md): все три описывают конвейер и
контракт пагинации как они были задуманы изначально, этот файл — как они
на самом деле выглядят после того, как SG Buddy выпустил другую форму
пагинации (`page`/`order` вместо `page_offset`, общее сообщение `Pagination`
вместо плоских `total_rows`/`total_pages`), и после доработки `parse.py` /
`resolve.py` / `gen.py` под домен `tables_model` (`dc.alias`, `dc.user`), где
стандартный набор из восьми запросов оказался неполным, и под
`user_domain_roles`, где выборки перестали отдавать строку своей таблицы. Читать после
генерации `.proto`, если контракт пагинации или набор запросов таблицы не
совпадает с тем, что описано в основной цепочке доков.

## Обязательных операций не осталось

`Create<Entity>` — обычный источник имени сущности (`entity`) и структуры
строки: `resolve.py` берёт их из типа возврата `Create<Entity>`, а не из
`Get<Entity>ById`, как было в самой первой версии.

Но и его может не быть. Таблица-справочник (`dc.calculation_type`) содержит
фиксированный список значений, клиенты его только читают — ни `Create`, ни
`Update`/`Delete` у неё нет. Тогда имя сущности и строка берутся из
`Get<E>ById`, а `Create`-часть не генерируется ни в одном слое (флаг
`has_create` в `model.json`). Требование при этом жёсткое: без `Create`
должен быть ровно один запрос вида `Get<E>ById` — иначе имя сущности взять
неоткуда, и это `Fail`, а не догадка по имени таблицы.

Остальные пять именованных операций опциональны и генерируются только если
реально есть в `query.sql`:

| Операция | Имя запроса | Что если нет |
|---|---|---|
| получить активную по id | `Get<E>ById` | не генерируется `GetById` ни в одном слое |
| получить удалённую по id | `GetDeleted<E>ById` | `Undelete<E>ById` теряет проверку существования перед восстановлением (см. ниже) |
| обновить | `Update<E>ById` | не генерируется вовсе |
| мягко удалить | `Delete<E>ById` | не генерируется вовсе |
| восстановить | `Undelete<E>ById` | не генерируется вовсе |

Отсутствие любой из них — не ошибка конвейера. Ошибка — запрос, который не
попал ни в одну из известных форм (см. ниже).

## Списочные запросы разбираются по форме, а не по имени

Раньше `Get<P>` и `GetDeleted<P>` были двумя жёстко зашитыми именами.
Теперь любой `:many`-запрос без обязательного аргумента-фильтра (аргументов
нет вовсе, либо структура параметров состоит только из полей пагинации —
см. ниже) попадает в общий список `lists` — независимо от того, как он
называется. Так `GetAliases` и `GetAliasesDeleted` (SG Buddy назвал
"выборку удалённых" суффиксом, а не префиксом `GetDeleted...`) обрабатываются
одинаково: генератору всё равно, что означает имя, важна только форма
запроса. На каждый элемент `lists` генерируется свой набор
converter/service/api-методов. Слайс-конвертер общий (`<Plural>ToProto`)
только у тех списков, что отдают строку своей таблицы; у join-выборки он
свой — см. "Строка ответа" ниже.

`Get<P>By<Fk>` (один голый скалярный аргумент-фильтр) по-прежнему уходит в
`fks`, `Get<E>By<Column>` (`:one`) — в `lookups`; для них форма не менялась.

Отдельная форма — список целиком, но с выбором направления сортировки
(`GetCalculationTypes`, `GetGroupLevelsDeleted`): страницы нет, поэтому sqlc
не заворачивает аргументы в структуру и отдаёт голый `order string`. Такой
запрос опознаётся по имени и типу единственного аргумента (`order`,
`string`) — иначе он ушёл бы в `fks` и генератор попытался бы проверить
`order` как id. В `model.json` это `arg_form: "order"`: сервис принимает
`order string`, api сначала зовёт `Validate<Query>` (там только проверка
самого `order`), конвертера у такого запроса нет — переносить нечего.

## Пагинация: что реально сделано в parse.py/resolve.py/gen.py

`pagination_go.md`/`pagination_proto.md` описывают план с плоским ответом
(`rows`/`total_rows`/`total_pages`) и `page_offset`. SG Buddy в итоге сделал
другую, более позднюю форму контракта — конвейер настроен под неё:

- **Параметры страницы** — структура `Params` с полями `PageLimit int32`
  (обязательно), `Page int32` (обязательно, номер страницы с единицы, не
  смещение), `Order string` (опционально, `"ASC"`/`"DESC"`/пусто) и
  `OrderBy string` (опционально, имя колонки сортировки — см. ниже). Любое
  другое поле в такой структуре считается фильтром (см. "Списочные запросы
  с фильтром"); список полей страницы и их типов зашит в `resolve.py`
  (`PAGE_FIELD_TYPES`, `REQUIRED_PAGE_FIELDS`).
- **Ответ считается постраничным**, если в proto-сообщении ровно два поля:
  список строк (`repeated`, имя любое — было `rows`, стало `data`) и
  `*Pagination` — сообщение, общее для всего файла (см. `pagination_proto.md`,
  "одна на файл, поля одни и те же везде"). Опознаётся по **типу** второго
  поля, не по имени.
- **`Pagination`** — фиксированно четыре поля: `page`, `per_page`,
  `total_items`, `total_pages`. Их порядок в `.proto` важен (конвейер читает
  позиционно — `resolve_pagination_fields`), конкретные Go-имена не важны.
- **Счётчик обязателен**: `Count<Query>` должен существовать, принимать один
  голый `int32`-аргумент (`page_limit`) и возвращать структуру ровно из двух
  полей — первое читается как «сколько всего строк», второе — «сколько всего
  страниц» (опять позиционно, не по имени: раньше поля назывались
  `total_rows`/`total_pages`, теперь `total_items`/`total_pages`).
- **`per_page` в ответе — это `PageLimit` из запроса**, а не что-то отдельно
  посчитанное: конвертер/api берут `params.PageLimit` напрямую. Тип API
  переименовал `page_limit` в `per_page` только в исходящем сообщении —
  дублирование поля с двумя именами, единый источник значения.
- **`Order`** валидируется как `v.StringIn("order", ..., "", "ASC", "DESC")`,
  только если это поле вообще есть у запроса (`resolve.py` помечает
  `order_field`); в SQL любое значение, кроме `"DESC"`, всё равно ведёт себя
  как `ASC` — проверка в API строже контракта осознанно.
- **`OrderBy`** — выбор колонки сортировки (`dc.database_cat`). Отличается от
  `Order` тем, что допустимые значения у каждого запроса свои и живут только
  в самом SQL: `CASE WHEN @order_by::text = 'name' THEN ...`. `.proto`
  перечисляет их в комментарии, но в `pb.go` комментарий не попадает, поэтому
  `parse.py` вычитывает значения прямо из тела запроса (`ORDER_BY_VALUE_RE`,
  ключ `order_by_values` в `parsed.json`), а `gen.py` собирает из них
  `v.StringIn("order_by", ..., "", <значения>)`. Поле есть, а сравнений в SQL
  нет — `Fail`: молча пропустить проверку нельзя, опечатка в имени колонки
  тогда тихо вернула бы сортировку по умолчанию. В параметры `Count<Query>`
  `OrderBy` не входит — он не сужает выборку.
- **`PageLimit == 0` → `validation.DefaultPageSize`, `Page == 0` → `1`** —
  подстановка в конвертере, как и было для `page_limit` раньше.
- Сервисный слой дёргает счётчик первым и не делает второй запрос при
  нулевом счётчике (поле берётся динамически, см. выше) — как и было
  задумано.

Если понадобится вернуть форму из `pagination_go.md`/`pagination_proto.md`
(плоский ответ без общего `Pagination`) — это уже не про правку резолвера
"на лету": там другая форма ответа и другие имена параметров, придётся
разводить два случая явно, а не молча поддерживать оба.

## Списочные запросы с фильтром

Ещё позже в `dc.host` появился `GetHostsSearchName` — постраничный список
с дополнительным аргументом-фильтром (`SearchName`, ищет по `name` через
`LIKE`) поверх обычных `Page`/`PageLimit`/`Order`. Раньше это било в `Fail`:
резолвер понимал только чистую пагинацию (в структуре параметров — ничего,
кроме `PAGE_FIELD_TYPES`) или голый скалярный FK-фильтр без пагинации.
Смешанная форма — своя, третья.

Отличие от разбора `pair_fields` (используется для `Create`/`Update`/
`Delete`/`Undelete`): там proto-поле обязано резолвиться в существующую
колонку `schema.sql` (или в `user_id` через `external_id`). Поле фильтра
списка — это условие в `WHERE`, а не запись в колонку, и может не совпадать
с ней 1:1 (`search_name` ищет по `name`, но это не обязательное правило —
имя поля фильтра вообще ничем не ограничено). Поэтому `resolve.py` парует
такие поля с одноимённым полем в `<Query>Request` только по имени
(`pair_filter_fields`), без проверки `schema.sql`.

- **Какие поля становятся фильтром**: любое поле структуры параметров
  `:many`-запроса сверх полей страницы (`PageLimit`/`Page`/`Order`/`OrderBy`),
  при условии, что его тип входит в `FILTER_FIELD_TYPES` (`bool`, `int64`,
  `int16`, `string`, `uuid.UUID`, `sql.NullInt64`, `sql.NullBool` — тот же
  набор, что понимает `req_to_param_expr` для переноса значения). Другой тип
  — `Fail`, а не молчаливый пропуск.
- **Счётчик** (`Count<Query>`) для отфильтрованного списка обязан принимать
  не голый `page_limit`, а структуру параметров из `PageLimit` и тех же
  полей фильтра (иначе подсчёт "всего страниц" не учитывал бы фильтр и
  разошёлся бы с самой выборкой). `resolve.py` сверяет набор полей счётчика
  с `{PageLimit} ∪ поля_фильтра` — не больше и не меньше.
- **Сервисный слой** сам собирает `countParams` из `params` перед вызовом
  счётчика (поля фильтра — с тем же именем, что и в структуре самой
  выборки; иначе типы `Count<Query>Params` и `<Query>Params` в Go не
  совпадают, и один в другой не передать напрямую, даже если поля
  одинаковые). Сама постраничная выборка (`repo.<Query>(ctx, params)`)
  и так получает `params` целиком — без изменений в шаблоне.
- **Валидация**: поля фильтра **не проверяются** — у них нет естественной
  границы длины (это не колонка `schema.sql`, а условие `WHERE`), и
  требовать непустоту тоже не всегда правильно (пустой `search_name` может
  означать "без фильтра"). Если для конкретного поля нужна проверка — это
  логика сверх шаблона, дописывается рядом, не в сгенерированный файл (см.
  "Где лежит код" в [generate_gprpc_go.md](generate_gprpc_go.md)).

### Необязательный фильтр: `sqlc.narg` ↔ `optional` в proto

`GetColumnCatsOptionalFilters`, `GetDatabaseCatsByHostIdDatabaseTypeId`,
`GetDatabaseCalculationsFiltered` и подобные фильтруют по нескольким
колонкам сразу, и каждое условие можно не задавать:

```sql
WHERE (sqlc.narg('host_id')::bigint IS NULL OR database_cat.host_id = sqlc.narg('host_id'))
```

sqlc делает такому параметру тип `sql.NullInt64` (`sql.NullBool` для
`boolean`), SG Buddy — `optional int64` / `optional bool` в `.proto`, то есть
`*int64` / `*bool` в `pb.go`. Пара разбирается в `gen.py` (`NULLABLE_PAIRS`)
и переносится хелперами `converter.ProtoToNullInt64` / `ProtoToNullBool` —
они лежат в рукописном `internal/converter/convert.go`, генератор их не
трогает.

Важная деталь: **значение берётся прямо из поля, а не из геттера**.
`req.GetHostId()` отдаёт `0` и на «не передан», и на явно переданный ноль —
presence в геттере теряется, а для `bool` это ещё и разница между «фильтр
`false`» и «фильтра нет». Поэтому шаблон пишет `req.HostId`, а от `nil`-req
защищается явной подменой на пустое сообщение в начале конвертера
(`req_guard` в `gen.py`); у остальных полей ту же защиту бесплатно дают
геттеры. Непереданный фильтр обязан доехать до SQL как `NULL` — на это
генерируется отдельный тест `Test<Query>OmitsAbsentFilters`.

Всё остальное как у обычного фильтра: поля входят в параметры `Count<Query>`
и не валидируются.

## Строка ответа: сущность или собственная строка запроса

Ещё позже SG Buddy начал отдавать `dc.user_domain_roles` и `dc.user_table_roles`
не голыми строками своих таблиц, а join-выборками: к колонкам самой таблицы
подмешаны `domain_roles.name`, `dc_user.name`, `table_cat.id` и прочее.
sqlc делает под такую выборку отдельную структуру `<Query>Row`, SG Buddy —
одноимённое proto-сообщение, и общий `<Entity>ToProto` такую строку не
перенесёт: у неё свой набор полей.

Раньше конвейер знал ровно одну строку на таблицу — ту, что вернул
`Create<Entity>`, — и любой другой тип строки был `Fail`. Теперь **у каждого
запроса своя строка**, и вид определяется по тому, что вернул репозиторий, а
не по имени запроса (`resolve_row` в `resolve.py`):

| Что вернул метод репозитория | Что генерируется |
|---|---|
| строку своей таблицы (`DcAlias`) | как раньше: `<Entity>ToProto` / `<Plural>ToProto` |
| собственную строку (`GetUserTableRolesesRow`) | `<Query>RowToProto` и, если запрос списочный, `<Query>RowsToProto` |

Правила для собственной строки:

- **proto-сообщение берётся из ответа, а не по имени**: `resp.Data` типа
  `[]*GetUserTableRolesesRow` или `resp.UserTableRoles` типа
  `*GetUserTableRolesByIdRow` — конвейер читает тип поля и в нём ищет пару
  каждому полю Go-структуры. Нет сообщения или нет поля — `Fail`.
- **Колонка в `schema.sql` не проверяется** (`pair_row_fields`), в отличие от
  `pair_fields`: `dc_user_name` — колонка соседней таблицы, а не своей.
  Проверять нечего и незачем: строка едет только наружу, ни в один
  `INSERT`/`UPDATE` её поля не попадают, границы длины ей не нужны.
- **`external_id` в такой строке не резолвится**: `dc_user_external_id`
  (`uuid.UUID` → `string`) — просто выбранная колонка соседней таблицы,
  а не конвенция резолва через `dc."user"` (см. «`external_id`: два разных
  случая» ниже).
- **`Get<E>ById` больше не обязан отдавать сущность.** Раньше это было
  жёсткое требование (и именно поэтому `GetColumnTypeById` чинили в
  источнике — см. ниже); теперь `GetUserTableRolesById` законно отдаёт
  `GetUserTableRolesByIdRow`. Требование осталось одно: ровно одно поле в
  `<Query>Response`.
- `optional int64` в такой строке (`dc_user_id`, `table_cat_id` — колонки
  `bigserial`, то есть `NOT NULL`, а SG Buddy пометил их `optional`)
  проходит по уже существующему правилу `int64 → *int64`
  (`converter.Int64ToProto`), отдельного случая не понадобилось.

`<Entity>ToProto` и `<Plural>ToProto` генерируются всегда, даже если ни одна
выборка их больше не использует (как в `dc.user_table_roles`, где все три
выборки — join). Это мёртвый код, а не ошибка: неиспользованная функция
сборку Go не ломает, в отличие от импорта.

## Ещё два типа необязательного фильтра

К паре `sqlc.narg` ↔ `optional` (см. выше) добавились строка и uuid —
`GetUserTableRolesesFiltered` фильтрует по имени пользователя, его
`external_id` и имени таблицы:

| sqlc | proto | Переносится |
|---|---|---|
| `sql.NullString` | `optional string` | `converter.ProtoToNullString` |
| `uuid.NullUUID` | `optional string` | `converter.ProtoToNullUUID` |

`ProtoToNullUUID` дописан в рукописный `internal/converter/convert.go` рядом
с остальными (`ProtoToNullString` там уже был); нераспознанная строка
становится `uuid.Nil`, как и в `ProtoToUUID`, — формат проверяет валидация,
а не конвертер. Значение по-прежнему берётся из поля, а не из геттера, и
такому конвертеру по-прежнему нужен `req_guard`.

## Шапка сервиса собирается по телу файла

`dc.user_domain_roles` — первая таблица без `Get<E>ById`. Проверок
существования перед `Delete`/`Undelete` у неё поэтому нет (это уже описано
выше), а вместе с ними из файла пропали единственные `errors.Is(err,
sql.ErrNoRows)` — и `gen.py` выписывал в шапку `database/sql` и `errors`,
которые никто не использует. В Go это не предупреждение, а ошибка сборки,
поэтому шапка сервиса теперь собирается после тела и по нему же:
`database/sql` — если в теле есть `sql.ErrNoRows`, `errors` — если есть
`errors.Is`/`errors.Join`, `customerrors` — если он там упомянут. Так же
устроена шапка тестов конвертера.

## Один файл `.proto` — несколько `service`

`user_domain_roles/v1` пришёл из SG Buddy с двумя сервисами —
`UserDomainRolesService` и `UserTableRolesService`, по одному на таблицу, как
это давно устроено в `tables/v1`. Обслуживает их одна Go-структура
`UserDomainRolesApiV1`, и два рукописных места нужно поправить руками —
генератор их не трогает (см. «Что перезаписывается, а что нет» в
[generate_gprpc_go.md](generate_gprpc_go.md)):

- `internal/api/userdomainrolesapiv1/init.go` — встроить
  `Unimplemented<Имя>ServiceServer` каждого сервиса, иначе структура не
  удовлетворяет интерфейсу;
- `datacatalogue/cmd/main.go` — `Register<Имя>ServiceServer` на каждый.

Первая сверка из [generate_gprpc_go.md](generate_gprpc_go.md#проверки-после-генерации)
этого не ловит: у всех RPC хендлеры есть, забыт только вызов регистрации.
Ловит третья, по `service` в `.proto`.

## `external_id`: два разных случая

Раньше конвенция была одна: proto-поле `<col>_external_id` резолвится в
`<col>_id` через `dc.user`. Теперь их два, и `resolve.py`/`pair_fields`
различает их по тому, есть ли у **самой таблицы запроса** своя колонка
`external_id`:

- Таблица **без** своей колонки `external_id` (например, `dc.alias`) —
  прежнее поведение: proto-поле `external_id` (или `<col>_external_id`)
  резолвится в `user_id` (или `<col>_id`) через
  `(SELECT u.id FROM dc."user" u WHERE u.external_id = ...)`.
- Таблица **со своей** колонкой `external_id` (`dc.user`) — поле `external_id`
  сопоставляется напрямую с этой колонкой, никакого резолва через подзапрос.

Это же правило поймало реальный баг в сгенерированном `query.sql`: `CreateUser`
резолвил `external_id` через подзапрос к `dc."user".id` (bigint в uuid-колонку) —
чинится в SG Buddy/`query.sql`, не в генераторе.

## `Update`/`Delete`/`Undelete`: теперь бывает форма параметров

Раньше `Delete<E>ById`/`Undelete<E>ById` всегда принимали голый `id int64`.
Теперь, если запрос заодно резолвит `user_id` через `external_id` (как в
`dc.alias`), sqlc заворачивает аргументы в структуру параметров — конвейер
понимает обе формы (`arg_form: "id" | "params"`) и генерирует разный код:
голый id — валидация через общий `validation.ValidateID`; структура —
собственная `Validate<Query>` и `To<Query>Params` конвертер, как у `Update`.

Ответ этих трёх операций тоже классифицируется по числу полей в
`<Query>Response`, а не по аннотации sqlc (`:one`/`:exec`):

| Полей в ответе | Форма | Что генерируется |
|---|---|---|
| 0 | `empty` | `return &Resp{}, nil` |
| 1, тип поля — сама сущность | `row` | как раньше: `RETURNING`, `EntityToProto(row)` |
| 1, тип поля — что-то другое | `field` | старое соглашение обёртки `google.protobuf.Empty`: `return &Resp{Field: &emptypb.Empty{}}, nil` |

`Undelete<E>ById` проверяет существование удалённой записи перед
восстановлением через `GetDeleted<E>ById` **только если тот слот есть**;
`Delete<E>ById` — аналогично через `Get<E>ById`. Нет слота — нет проверки,
запрос идёт прямо в репозиторий.

## Где лежит код

Все правки — в трёх файлах основного конвейера, `custom_domains`
(`parse_custom.py`/`resolve_custom.py`/`gen_custom.py`) не тронуты:

- [deploy/generators/parse.py](../../../deploy/generators/parse.py) —
  фикс `varchar(n)` (см. ниже) и вычитывание допустимых значений `order_by`
  из тел запросов (`order_by_values` в `parsed.json`).
- [deploy/generators/resolve.py](../../../deploy/generators/resolve.py) —
  вся логика классификации операций и списков.
- [deploy/generators/gen.py](../../../deploy/generators/gen.py) — шаблоны
  под новую форму модели.

Последний раунд (собственная строка запроса, `sql.NullString`/`uuid.NullUUID`,
шапка сервиса по телу файла) `parse.py` не трогал вовсе: он и так складывал в
`parsed.json` всё нужное — структуры из `query.sql.go` и сообщения из
`pb.go`. Правки только в `resolve.py` (`resolve_row`, `pair_row_fields`) и
`gen.py` (шаблоны конвертеров строк и сборка импортов).

Заодно в `parse.py` подтянут баг, который [generate_grpc_go_non_crud.md](generate_grpc_go_non_crud.md)
уже описывал для `parse_custom.py`: `parse_schema()` искала границу varchar
только по `character varying(n)`, `dc.user.name` в `schema.sql` записан как
`varchar(512)` — теперь регулярка принимает оба варианта.

## Что чинится в источнике, а не в генераторе

Конвейер падает на расхождении, и иногда правильный ответ — поправить
`query.sql`/`.proto` и перегенерировать (`task sqlc:gen`, `task proto:gen`),
а не учить резолвер новой форме. Так было с `CreateUser` (см. выше) и так же
разобрали очередную партию из SG Buddy:

- `GetColumnTypeById` и `GetDatabaseCalculationById` не выбирали `id`. sqlc
  делал на них отдельный `Get<E>ByIdRow`, а SG Buddy — одноимённое
  proto-сообщение вместо сущности. Остальные 14 выборок по id отдают строку
  целиком; поддерживать вторую форму строки ради двух запросов дороже, чем
  дописать `id` в `SELECT`.
- `UndeleteGroupLevels` — без суффикса `ById`, хотя аргумент именно id.
  Переименован в `UndeleteGroupLevelsById` в `query.sql` и в `.proto`: имя
  операции конвейер сопоставляет точно, а не «примерно».
- `UpdateSchemaCatById` принимал `created_at`, `DeleteSchemaCatById` —
  `updated_at`. Во всём остальном файле время ставит сама база (`now()`), а
  `created_at` при обновлении не трогают вовсе. Параметры убраны из SQL и
  соответствующие поля — из proto-запросов.
- `GetUserTableRolesesFiltered` и его счётчик приводили необязательный фильтр
  к `sqlc.narg('table_cat_id')::bigserial`. `bigserial` — не тип, а сокращение
  для `bigint` + последовательность, и существует только в объявлении колонки:
  `$N::bigserial` Postgres отвергает («type "bigserial" does not exist»). sqlc
  разбирает такой каст молча и даёт правильный `sql.NullInt64`, так что
  сломался бы только запуск запроса. Заменено на `::bigint`; сгенерированный
  Go при этом не меняется.

Отдельно, не ошибка, но расхождение: `DeleteUserDomainRolesById` не трогает
`updated_at`, хотя `DeleteUserTableRolesById` рядом его ставит. Обе формы
конвейер принимает, поправить стоит в SG Buddy.

## Проверки не изменились

Обе сверки и команды из [generate_gprpc_go.md](generate_gprpc_go.md#проверки-после-генерации)
работают как раньше. Единственная ожидаемая «расходимость» — `Count<Query>`
в списке методов репозитория без своего метода сервиса: он обёрнут внутри
постраничного метода, это норма (см. `pagination_go.md`).
