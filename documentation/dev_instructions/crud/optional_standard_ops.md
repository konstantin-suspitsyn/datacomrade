# Необязательные стандартные операции и пагинация — как это реально устроено

Дополнение к [generate_gprpc_go.md](generate_gprpc_go.md), [pagination_go.md](pagination_go.md)
и [pagination_proto.md](pagination_proto.md): все три описывают конвейер и
контракт пагинации как они были задуманы изначально, этот файл — как они
на самом деле выглядят после того, как SG Buddy выпустил другую форму
пагинации (`page`/`order` вместо `page_offset`, общее сообщение `Pagination`
вместо плоских `total_rows`/`total_pages`), и после доработки `parse.py` /
`resolve.py` / `gen.py` под домен `tables_model` (`dc.alias`, `dc.user`), где
стандартный набор из восьми запросов оказался неполным. Читать после
генерации `.proto`, если контракт пагинации или набор запросов таблицы не
совпадает с тем, что описано в основной цепочке доков.

## Обязательна только одна операция

`Create<Entity>` — единственный запрос, без которого таблица не соберётся:
из него `resolve.py` берёт имя сущности (`entity`) и структуру строки
(тип возврата `Create<Entity>`, а не `Get<Entity>ById`, как было раньше —
`GetById` тоже может отсутствовать).

Остальные пять именованных операций опциональны и генерируются только если
реально есть в `query.sql`:

| Операция | Имя запроса | Что если нет |
|---|---|---|
| получить активную по id | `Get<E>ById` | не генерируется `GetById` ни в одном слое |
| получить удалённую по id | `GetDeleted<E>ById` | `Undelete<E>ById` теряет проверку существования перед восстановлением (см. ниже) |
| обновить | `Update<E>ById` | не генерируется вовсе |
| мягко удалить | `Delete<E>ById` | не генерируется вовсе |
| восстановить | `Undelete<E>ById` | не генерируется вовсе |

Отсутствие любой из них — не ошибка конвейера. Ошибка — запрос, который не
попал ни в одну из известных форм (см. ниже).

## Списочные запросы разбираются по форме, а не по имени

Раньше `Get<P>` и `GetDeleted<P>` были двумя жёстко зашитыми именами.
Теперь любой `:many`-запрос без обязательного аргумента-фильтра (аргументов
нет вовсе, либо структура параметров состоит только из полей пагинации —
см. ниже) попадает в общий список `lists` — независимо от того, как он
называется. Так `GetAliases` и `GetAliasesDeleted` (SG Buddy назвал
"выборку удалённых" суффиксом, а не префиксом `GetDeleted...`) обрабатываются
одинаково: генератору всё равно, что означает имя, важна только форма
запроса. На каждый элемент `lists` генерируется свой набор
converter/service/api-методов; общий у них только слайс-конвертер
`<Plural>ToProto`.

`Get<P>By<Fk>` (один голый скалярный аргумент-фильтр) по-прежнему уходит в
`fks`, `Get<E>By<Column>` (`:one`) — в `lookups`; для них форма не менялась.

## Пагинация: что реально сделано в parse.py/resolve.py/gen.py

`pagination_go.md`/`pagination_proto.md` описывают план с плоским ответом
(`rows`/`total_rows`/`total_pages`) и `page_offset`. SG Buddy в итоге сделал
другую, более позднюю форму контракта — конвейер настроен под неё:

- **Параметры страницы** — структура `Params` с полями `PageLimit int32`
  (обязательно), `Page int32` (обязательно, номер страницы с единицы, не
  смещение) и `Order string` (опционально, `"ASC"`/`"DESC"`/пусто). Любое
  другое поле в такой структуре — `Fail`; список допустимых полей и их типов
  зашит в `resolve.py` (`PAGE_FIELD_TYPES`, `REQUIRED_PAGE_FIELDS`).
- **Ответ считается постраничным**, если в proto-сообщении ровно два поля:
  список строк (`repeated`, имя любое — было `rows`, стало `data`) и
  `*Pagination` — сообщение, общее для всего файла (см. `pagination_proto.md`,
  "одна на файл, поля одни и те же везде"). Опознаётся по **типу** второго
  поля, не по имени.
- **`Pagination`** — фиксированно четыре поля: `page`, `per_page`,
  `total_items`, `total_pages`. Их порядок в `.proto` важен (конвейер читает
  позиционно — `resolve_pagination_fields`), конкретные Go-имена не важны.
- **Счётчик обязателен**: `Count<Query>` должен существовать, принимать один
  голый `int32`-аргумент (`page_limit`) и возвращать структуру ровно из двух
  полей — первое читается как «сколько всего строк», второе — «сколько всего
  страниц» (опять позиционно, не по имени: раньше поля назывались
  `total_rows`/`total_pages`, теперь `total_items`/`total_pages`).
- **`per_page` в ответе — это `PageLimit` из запроса**, а не что-то отдельно
  посчитанное: конвертер/api берут `params.PageLimit` напрямую. Тип API
  переименовал `page_limit` в `per_page` только в исходящем сообщении —
  дублирование поля с двумя именами, единый источник значения.
- **`Order`** валидируется как `v.StringIn("order", ..., "", "ASC", "DESC")`,
  только если это поле вообще есть у запроса (`resolve.py` помечает
  `order_field`); в SQL любое значение, кроме `"DESC"`, всё равно ведёт себя
  как `ASC` — проверка в API строже контракта осознанно.
- **`PageLimit == 0` → `validation.DefaultPageSize`, `Page == 0` → `1`** —
  подстановка в конвертере, как и было для `page_limit` раньше.
- Сервисный слой дёргает счётчик первым и не делает второй запрос при
  нулевом счётчике (поле берётся динамически, см. выше) — как и было
  задумано.

Если понадобится вернуть форму из `pagination_go.md`/`pagination_proto.md`
(плоский ответ без общего `Pagination`) — это уже не про правку резолвера
"на лету": там другая форма ответа и другие имена параметров, придётся
разводить два случая явно, а не молча поддерживать оба.

## Списочные запросы с фильтром

Ещё позже в `dc.host` появился `GetHostsSearchName` — постраничный список
с дополнительным аргументом-фильтром (`SearchName`, ищет по `name` через
`LIKE`) поверх обычных `Page`/`PageLimit`/`Order`. Раньше это било в `Fail`:
резолвер понимал только чистую пагинацию (в структуре параметров — ничего,
кроме `PAGE_FIELD_TYPES`) или голый скалярный FK-фильтр без пагинации.
Смешанная форма — своя, третья.

Отличие от разбора `pair_fields` (используется для `Create`/`Update`/
`Delete`/`Undelete`): там proto-поле обязано резолвиться в существующую
колонку `schema.sql` (или в `user_id` через `external_id`). Поле фильтра
списка — это условие в `WHERE`, а не запись в колонку, и может не совпадать
с ней 1:1 (`search_name` ищет по `name`, но это не обязательное правило —
имя поля фильтра вообще ничем не ограничено). Поэтому `resolve.py` парует
такие поля с одноимённым полем в `<Query>Request` только по имени
(`pair_filter_fields`), без проверки `schema.sql`.

- **Какие поля становятся фильтром**: любое поле структуры параметров
  `:many`-запроса сверх `PageLimit`/`Page`/`Order`, при условии, что его тип
  входит в `FILTER_FIELD_TYPES` (`bool`, `int64`, `int16`, `string`,
  `uuid.UUID` — тот же набор, что понимает `req_to_param_expr` для прямого
  переноса значения). Другой тип — `Fail`, а не молчаливый пропуск.
- **Счётчик** (`Count<Query>`) для отфильтрованного списка обязан принимать
  не голый `page_limit`, а структуру параметров из `PageLimit` и тех же
  полей фильтра (иначе подсчёт "всего страниц" не учитывал бы фильтр и
  разошёлся бы с самой выборкой). `resolve.py` сверяет набор полей счётчика
  с `{PageLimit} ∪ поля_фильтра` — не больше и не меньше.
- **Сервисный слой** сам собирает `countParams` из `params` перед вызовом
  счётчика (поля фильтра — с тем же именем, что и в структуре самой
  выборки; иначе типы `Count<Query>Params` и `<Query>Params` в Go не
  совпадают, и один в другой не передать напрямую, даже если поля
  одинаковые). Сама постраничная выборка (`repo.<Query>(ctx, params)`)
  и так получает `params` целиком — без изменений в шаблоне.
- **Валидация**: поля фильтра **не проверяются** — у них нет естественной
  границы длины (это не колонка `schema.sql`, а условие `WHERE`), и
  требовать непустоту тоже не всегда правильно (пустой `search_name` может
  означать "без фильтра"). Если для конкретного поля нужна проверка — это
  логика сверх шаблона, дописывается рядом, не в сгенерированный файл (см.
  "Где лежит код" в [generate_gprpc_go.md](generate_gprpc_go.md)).

## `external_id`: два разных случая

Раньше конвенция была одна: proto-поле `<col>_external_id` резолвится в
`<col>_id` через `dc.user`. Теперь их два, и `resolve.py`/`pair_fields`
различает их по тому, есть ли у **самой таблицы запроса** своя колонка
`external_id`:

- Таблица **без** своей колонки `external_id` (например, `dc.alias`) —
  прежнее поведение: proto-поле `external_id` (или `<col>_external_id`)
  резолвится в `user_id` (или `<col>_id`) через
  `(SELECT u.id FROM dc."user" u WHERE u.external_id = ...)`.
- Таблица **со своей** колонкой `external_id` (`dc.user`) — поле `external_id`
  сопоставляется напрямую с этой колонкой, никакого резолва через подзапрос.

Это же правило поймало реальный баг в сгенерированном `query.sql`: `CreateUser`
резолвил `external_id` через подзапрос к `dc."user".id` (bigint в uuid-колонку) —
чинится в SG Buddy/`query.sql`, не в генераторе.

## `Update`/`Delete`/`Undelete`: теперь бывает форма параметров

Раньше `Delete<E>ById`/`Undelete<E>ById` всегда принимали голый `id int64`.
Теперь, если запрос заодно резолвит `user_id` через `external_id` (как в
`dc.alias`), sqlc заворачивает аргументы в структуру параметров — конвейер
понимает обе формы (`arg_form: "id" | "params"`) и генерирует разный код:
голый id — валидация через общий `validation.ValidateID`; структура —
собственная `Validate<Query>` и `To<Query>Params` конвертер, как у `Update`.

Ответ этих трёх операций тоже классифицируется по числу полей в
`<Query>Response`, а не по аннотации sqlc (`:one`/`:exec`):

| Полей в ответе | Форма | Что генерируется |
|---|---|---|
| 0 | `empty` | `return &Resp{}, nil` |
| 1, тип поля — сама сущность | `row` | как раньше: `RETURNING`, `EntityToProto(row)` |
| 1, тип поля — что-то другое | `field` | старое соглашение обёртки `google.protobuf.Empty`: `return &Resp{Field: &emptypb.Empty{}}, nil` |

`Undelete<E>ById` проверяет существование удалённой записи перед
восстановлением через `GetDeleted<E>ById` **только если тот слот есть**;
`Delete<E>ById` — аналогично через `Get<E>ById`. Нет слота — нет проверки,
запрос идёт прямо в репозиторий.

## Где лежит код

Все правки — в трёх файлах основного конвейера, `custom_domains`
(`parse_custom.py`/`resolve_custom.py`/`gen_custom.py`) не тронуты:

- [deploy/generators/parse.py](../../../deploy/generators/parse.py) —
  только фикс `varchar(n)` (см. ниже).
- [deploy/generators/resolve.py](../../../deploy/generators/resolve.py) —
  вся логика классификации операций и списков.
- [deploy/generators/gen.py](../../../deploy/generators/gen.py) — шаблоны
  под новую форму модели.

Заодно в `parse.py` подтянут баг, который [generate_grpc_go_non_crud.md](generate_grpc_go_non_crud.md)
уже описывал для `parse_custom.py`: `parse_schema()` искала границу varchar
только по `character varying(n)`, `dc.user.name` в `schema.sql` записан как
`varchar(512)` — теперь регулярка принимает оба варианта.

## Проверки не изменились

Обе сверки и команды из [generate_gprpc_go.md](generate_gprpc_go.md#проверки-после-генерации)
работают как раньше. Единственная ожидаемая «расходимость» — `Count<Query>`
в списке методов репозитория без своего метода сервиса: он обёрнут внутри
постраничного метода, это норма (см. `pagination_go.md`).
