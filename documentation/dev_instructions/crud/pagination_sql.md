# Пагинация: шаг 1, запросы sqlc

Постраничную выдачу собирает **SG Buddy** —
<https://github.com/konstantin-suspitsyn/sg_buddy>: в настройках выборки
включается признак постраничности, и программа сама пишет пару запросов.
Руками SQL не правится.

Первый шаг цепочки пагинации:
**этот файл** → [pagination_proto.md](pagination_proto.md) → [pagination_go.md](pagination_go.md).
Общие правила генерации `query.sql` — в [standard_crud.md](standard_crud.md).

## Что включается в настройках

У выборки (`READ`) есть флаг постраничности и списки сортировки:

| Ключ `schema.json` | Что задаёт |
|---|---|
| `Pagination` | включает постраничность у этой выборки |
| `order_by` | колонки, по которым сортируем всегда |
| `order_by_optional` | колонки, сортировку по которым включает вызывающий |

Ответ на вопрос «какие колонки вообще можно выбрать для сортировки» живёт
здесь же, в `schema.json`, и является контрактом со шлюзом и фронтендом:
что не отмечено — того в API нет.

## Пара запросов

Включённая постраничность даёт **два** запроса: данные и счётчики. Имя
счётчика — `Count<имя выборки>`.

```sql
-- name: GetAliases :many
SELECT
    alias.id,
    alias.name,
    alias.description,
    alias.created_at,
    alias.updated_at,
    alias.is_deleted,
    alias.user_id
FROM dc.alias
ORDER BY alias.id
LIMIT @page_limit::int OFFSET @page_offset::int;

-- name: CountGetAliases :one
SELECT
    count(*)                                                        AS total_rows,
    ceil(count(*)::numeric / GREATEST(@page_limit::int, 1))::bigint AS total_pages
FROM dc.alias;
```

Что здесь важно:

- параметры страницы — `@page_limit::int` и `@page_offset::int`; sqlc назовёт
  их `PageLimit` и `PageOffset`;
- счётчик возвращает **и общее число строк, и общее число страниц** — арифметики
  пагинации в Go нет;
- `GREATEST(@page_limit::int, 1)` — защита от деления на ноль: запрос не должен
  зависеть от того, дошёл ли до него валидатор;
- условия отбора у счётчика те же, что у данных, иначе он считает не тот набор.

## Сортировка

`ORDER BY` у списочной выборки есть всегда, даже если ничего не отмечено: без
него Postgres волен вернуть строки в любом порядке, и страницы начинают то
повторять строки, то терять их.

Обязательные колонки дают простой список:

```sql
ORDER BY alias.name, alias.id
```

Необязательные становятся булевыми параметрами `@order_by_<колонка>::boolean`
и собираются в один `CASE`, где вызывающий включает нужную сортировку флагом:

```sql
ORDER BY
    CASE WHEN @order_by_name::boolean = true THEN alias.name
         WHEN @order_by_created_at::boolean = true THEN alias.created_at
         ELSE alias.id END
```

`ELSE` обязателен — без него `CASE` вернул бы `NULL` и порядок пропал бы
совсем. В `ELSE` идёт первая обычная колонка сортировки, а если таких нет —
первая колонка таблицы.

**Ветки `CASE` обязаны быть одного типа.** Postgres не выполнит запрос, где в
одном `CASE` встретились `character varying` и `bigint`, — он падает с
`CASE types character varying and bigint cannot be matched`. Программа проверяет
это сама и пишет в список проблем; чинится выбором колонок, а не правкой SQL.

## Проверки

```bash
grep -c "^-- name:" datacatalogue/db/sqlc/tables_model/query.sql
```

Число выросло на два на каждую включённую постраничную выборку. Дальше
`task sqlc:gen` — в репозитории появятся `PageLimit`/`PageOffset` в структуре
параметров и `Count<имя>Row` со счётчиками.

Проверка на живой базе (пагинация — то место, где ошибка видна только в
данных): две соседние страницы по 5 строк не пересекаются и в сумме совпадают
с первой страницей по 10.

## Что не входит

- **`DESC`.** Порядок только по возрастанию.
- **Keyset/cursor-пагинация.** `OFFSET` линейно деградирует на больших сдвигах;
  для каталога метаданных (тысячи строк) это неважно. Таблице на миллионы строк
  нужен курсор, а не этот шаблон.
- **Согласованность счётчика и страницы.** Это два запроса вне общей
  транзакции: между ними строку могут вставить, и `total_rows` разойдётся со
  страницей на единицу. Осознанный размен на простоту.
