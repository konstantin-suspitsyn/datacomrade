# Пагинация: шаг 2, .proto

Контракт постраничной выборки пишет **SG Buddy** —
<https://github.com/konstantin-suspitsyn/sg_buddy>, вместе с `query.sql` и из
тех же настроек. Отдельного действия для `.proto` нет.

Второй шаг цепочки пагинации:
[pagination_sql.md](pagination_sql.md) → **этот файл** → [pagination_go.md](pagination_go.md).
Общие правила контракта — в [proto_based_on_crud.md](proto_based_on_crud.md).

## Что получается

Параметры страницы и счётчики лежат **плоско в сообщениях самой выборки** —
отдельного сообщения `Pagination` и общего файла на все домены нет:

```proto
// Выборка GetAliases: параметры вызова. Порядок по умолчанию — id.
message GetAliasesRequest {
  int32 page_limit = 1;
  int32 page_offset = 2;
}

// Выборка GetAliases: страница строк и счётчики всей выборки.
message GetAliasesResponse {
  repeated Alias rows = 1;
  int64 total_rows = 2;
  int64 total_pages = 3;
}
```

- имена полей совпадают с параметрами SQL (`@page_limit` → `page_limit`),
  чтобы контракт и запрос читались как одно целое;
- записи всегда в поле `rows`, счётчики — рядом с ними: клиент получает
  страницу и её состояние одним ответом;
- счётчики приезжают из парного запроса `Count<имя выборки>`; собственного RPC
  у него нет — его дёргает сервис;
- если у выборки задан явный список колонок, строкой ответа будет `<Имя>Row`,
  а не сообщение всей таблицы;
- необязательные сортировки добавляют в `Request` булевы поля
  `order_by_<колонка>` — по одному на отмеченную колонку.

## Проверки

Постраничные выборки описаны в контракте и по данным, и по счётчикам:

```bash
grep -c "total_pages" shared/proto/tables/v1/tables.proto; grep -c "page_limit" shared/proto/tables/v1/tables.proto
```

Первое число — количество постраничных ответов, второе — запросов; они
обязаны совпасть. Затем `task proto:lint` и `task proto:gen`.

Править `.proto` руками бессмысленно: следующее сохранение в программе
перезапишет файл целиком.
